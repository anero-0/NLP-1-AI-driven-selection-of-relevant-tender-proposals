Этот документ создан специально для того, чтобы ты мог уверенно защитить свою часть проекта. Здесь подробно описана архитектура веб-приложения, используемые технологии и алгоритмы работы «под капотом».

## 1. Общая архитектура и стек технологий

Твоя задача заключалась в том, чтобы "завернуть" ML-модель Даши в удобный пользовательский продукт, которым сможет пользоваться конечный заказчик (Мария) без знания программирования.

**Стек:**
- **Сервер (Backend):** Python 3 + фреймворк **FastAPI**. FastAPI был выбран за его высокую скорость работы, асинхронность и простоту создания роутов. Сервер запускается через ASGI-сервер **Uvicorn**.
- **Фронтенд (Frontend):** Написан без тяжелых фреймворков (Vanilla HTML5 / CSS3 / JavaScript) для максимальной легковесности. Шаблонизация страниц происходит на сервере с помощью **Jinja2** (FastAPI из коробки умеет рендерить HTML через Jinja2).
- **Библиотеки для работы с данными:** `openpyxl` (для тонкой работы с Excel-файлами: чтение скрытых ссылок, заливка ячеек цветом) и `pandas` (используется как прослойка для передачи данных в ML-модель).

---

## 2. Как работает Backend (`main.py`)

Сервер в `main.py` работает как дирижёр. Он содержит три основных маршрута (endpoints):
1. **`GET /`** — отдаёт главную страницу `index.html` (форма для Drag-and-Drop загрузки файла).
2. **`POST /upload`** — принимает загруженный файл (multipart/form-data), читает его в память, передает в парсер (`parser.py`), затем передает результат в скорер (`scorer.py`), сохраняет отскоренные данные во временное хранилище сессии и делает редирект (перенаправление) на страницу результатов с уникальным ID сессии.
3. **`GET /results`** — достаёт данные из сессии по ID и рендерит `results.html`, куда передает готовый массив словарей с тендерами.

**Управление состоянием (Сессии):** 
FastAPI по умолчанию не хранит состояние между запросами. Чтобы передать распарсенные данные со страницы `/upload` на страницу `/results` и `/download`, реализован простейший In-Memory кэш (словарь `_sessions` в `main.py`). Каждому файлу присваивается уникальный `uuid4()`, который передается в URL параметром `sid`.

## 3. Как работает Парсер (`app/parser.py`)

Обычное чтение через `pandas.read_excel` здесь не работало по двум причинам:
1. Выгрузки Контура имеют "двухэтажные" заголовки (первая строка содержит фильтры, а вторая — сами названия колонок).
2. Самая большая проблема — ссылки на карточки тендеров скрыты **внутри** ячеек Excel (гиперссылки). `pandas` их игнорирует и читает только видимый текст.

Поэтому ты написал кастомный парсер на `openpyxl`.
**Алгоритм работы:**
1. Парсер загружает бинарный поток загруженного файла (`BytesIO`).
2. Считывает вторую строку (`row[1]`) в качестве заголовков таблицы.
3. Идет циклом по всем остальным строкам. Если в ячейке, соответствующей колонке "Название", есть свойство `cell.hyperlink`, парсер извлекает `cell.hyperlink.target` и сохраняет как отдельное поле `link` в словаре.
4. На выходе получается чистый список словарей (List of Dicts), где каждый словарь — это один тендер с ключами: `name`, `price`, `region`, `pub_date`, `deadline`, `link` и т.д.

## 4. Интеграция ML и Скорер (`app/scorer.py`)

Когда парсер вернул список словарей, его принимает функция `score_records`. Здесь происходит магия состыковки Web-части и Data Science.

**Алгоритм:**
1. **Ленивая загрузка (Lazy Loading):** При старте сервера или при первом обращении функция `_get_model()` загружает бинарный файл модели `pipeline.joblib` и порог отсечения `threshold.joblib` с помощью библиотеки `joblib`.
2. **Перепаковка данных:** Словарь собирается в `pandas.DataFrame` с колонками на русском языке (так, как того ожидает скрипт Даши `features.py`).
3. **Предобработка (Feature Engineering):** Датафрейм прогоняется через функцию `features.build_features(df)`, которая чистит текст, считает разницу в датах (срочность) и готовит признаки.
4. **Предикт:** Вызывается `model.predict_proba(df)[:, 1]` — это возвращает вероятность того, что тендер интересен (число от 0.0 до 1.0).
5. **Нормировка и Масштабирование:** Чтобы цвета в UI отображались логично, ты написал алгоритм нормировки:
   - Если вероятность выше порога отсечения Даши (`0.106`), балл пересчитывается так, чтобы он попал в диапазон от **50 до 100** (жёлтый и зеленый цвета).
   - Если ниже порога — в диапазон **от 0 до 49** (красный цвет).
6. Записи сортируются по убыванию балла, чтобы самые интересные были наверху.

## 5. Генерация красивых отчётов (`app/exporter.py`)

На странице результатов заказчик может нажать кнопку "Скачать xlsx". Вызывается `exporter.py`, который делает обратную конвертацию: из списка словарей обратно в `.xlsx` файл.

**Особенности генерации (через `openpyxl`):**
1. Создаётся новый Excel-лист. Записывается красивая шапка таблицы.
2. В цикле записываются тендеры. В колонку "Название" программно вставляется формула `=HYPERLINK("...", "текст")`, чтобы ссылка осталась кликабельной.
3. В зависимости от целочисленного балла (от 0 до 100), ячейка с баллом красится:
   - `score >= 70`: зеленая заливка (`PatternFill`).
   - `40 <= score < 70`: желтая заливка.
   - `< 40`: красная заливка.
4. Документ закрепляет верхнюю строчку (`freeze_panes = 'A2'`) и регулирует ширину колонок для удобного чтения.

## 6. Как работает Frontend

- **Jinja2:** Шаблонизатор подставляет данные (балл, название, ссылки) в HTML-каркас. Например, цикл `{% for r in records %}` на странице `results.html` строит строки таблицы `<tr>`.
- **Vanilla JS (`app.js`):** Написан без React/Vue. Он отвечает за:
  - Drag-and-Drop загрузку (показывает пунктирную рамку при наведении файла).
  - Сортировку таблицы прямо в браузере при клике на заголовок колонки (чтобы не дергать сервер).
  - Ползунок фильтрации (скрывает строки `<tr>`, где балл ниже установленного, используя `display: none`).
- **Стилизация (`style.css`):** Тёмная тема с неоновыми (glassmorphism) элементами. Использованы CSS-переменные для гибкости, Flexbox для сеток.
